# 单篇文档写作：类型细则

> 配套主方案 `novel-studio-tech-design.md` 的第 1.4 节与第 9.5 节。
> 本文回答一个问题：历史、时政、技术、生活推荐这四类单篇，**到底靠什么保证质量**。

## 1. 单篇与长篇的根本差别

长篇的敌人是「不一致」：人物记错、时间线乱、伏笔断。所以它需要图谱与状态卡。
单篇的敌人是「不准确、不具体、不像人话」：编造数据、通篇空话、结构松散。所以它需要**素材、模板、术语表**。

| 维度 | 长篇 | 单篇 |
|---|---|---|
| 主要失败模式 | 前后矛盾、人物崩坏 | 编造事实、空洞套话、结构混乱 |
| 核心输入 | 前文 + 设定 + 图谱 | 素材 + 模板骨架 + 受众 |
| 生成单位 | 章（3,000 字，多次续写） | 节（600-1,500 字，一次成型） |
| 一次成功的关键 | 上下文正确 | 素材足够 + 骨架明确 |
| 检查重点 | 状态冲突 | 来源缺失、术语漂移、时效过期 |

一句话：**长篇靠记忆，单篇靠证据。**

## 2. 三个正交维度：模板 / 渠道 / 文风

「怎么算一篇好稿」的约束一度挤在两个枚举里（`kind` / `subtype`），于是「历史 + 公众号」这种组合无法表达——公众号是**平台**，不是一种内容领域，和「历史」根本不在同一个轴上。
现在拆成三个互不替代的维度：

| 维度 | 回答什么 | 存在哪 | 注入的桶 |
|---|---|---|---|
| 模板 `template` | 写什么：几节、每节管什么、每节多少字 | `templates` 表（YAML 播种内置行） | S0 |
| 渠道 `channel` | 发到哪：段落节奏、配图占位、字数区间、平台禁忌 | `works.channel` + `content-types.yaml` 的 `channels` 段 | S1 |
| 文风 `style` | 怎么说：人称、时态、语气、禁忌、旧文画像 | `works.style_json` + 文风画像 | S1 |

一个作品 = **模板 × 渠道 × 文风**。换模板不改语气，换渠道不改骨架。

### 2.1 模板：骨架

模板只负责「骨架 + 这一套骨架的写法备注」，对应 `templates` 表：

```json
{
  "id": "tpl_tech_solution",
  "kind": "article",
  "subtype": "tech",
  "channel": "",
  "name": "技术方案 / 踩坑记录",
  "outline": [
    {"heading": "背景与问题", "prompt": "说明要解决什么问题、现状痛点是什么", "target_words": 600},
    {"heading": "方案概述", "prompt": "给出核心思路与选型理由，不展开细节", "target_words": 800},
    {"heading": "落地步骤", "prompt": "分步骤说明，每步含命令/配置/预期输出", "target_words": 1500},
    {"heading": "常见坑", "prompt": "列出 3-5 个实际遇到的坑、现象与解决办法", "target_words": 1000},
    {"heading": "结论", "prompt": "适用边界，什么场景不要用这套", "target_words": 400}
  ],
  "style_prompt": "面向有经验的后端工程师；直接、不寒暄；不用「首先/其次/最后」；代码块必须带语言标注",
  "checks": ["term_inconsistent", "structure_incomplete", "citation_missing"]
}
```

`outline[].target_words` 是**软约束**：网页端模型不会精确服从字数，但给出目标能避免「一节写 200 字」或「一节写 5,000 字」的失控。实际偏差通常在 ±40%。

模板还带一批「这套骨架怎么用」的元数据：`channel`（专为某个平台定的骨架，可为空）、`tags_json`、`is_default`（同一 `kind+subtype+channel` 组内的默认）、`pinned`（收藏，列表置顶）、`note`（什么时候用这一套）、`source_work_id`（从哪本作品沉淀来的）。

### 2.2 渠道：平台节奏

`content-types.yaml` 的顶层 `channels` 段，与 `kinds` 平级，**任何文种都能选**：

```yaml
channels:
  wechat:
    label: 公众号
    target_words: 2500
    style_prompt: 口语，每段不超过三行（约 100 字），段间空一行；小标题直给结论
    instructions: 每 2-3 段插一个「[图：画面描述]」占位；结尾留互动，不用「点赞转发加关注」
    checks_append: [absolute_claim]
```

渠道与文种在装配层走两条互不覆盖的路：

- 渠道的 `style_prompt` / `instructions` 落独立键 `channel_style_prompt` / `channel_instructions`，**不拼进**文种的 `style_prompt`。S1 里它带「平台要求（公众号）：」前缀单独成段——文种说「区分史料与推断」，平台说「每段不超过三行」，混成一条时模型会拿其中一条把另一条顶掉。
- `label`、`budget_chars`、`layers` 仍归文种管。叠一个渠道不会把「历史」顶成「公众号」，两个维度的名字都在场。
- `checks_append` 与文种的检查项**合并去重**：同一条规则两头都挂时只出现一次。

S0 还会多出一行 `渠道：公众号`。骨架的长度节奏本来就是按平台定的（公众号一节 800 字、知乎可以 1,500），模型看到这两个字才对得上后面的字数要求。

一次性任务（改写 / 压缩）没有作品行可挂，用 `requirements_text(resolved)` 拼一段汇总文本：文体在前、平台在后，两段不混。

### 2.3 文风：语气

`works.style_json`（人称、时态、语气、禁忌）与文风画像（贴过的旧文统计出的句长、常用词）都进 S1。它比渠道更靠后：先平台节奏，再个人习惯——两者冲突时保留作者本人的说话方式，因为读者关注的是人。

### 2.4 模板怎么被挑中：六级优先链

新建作品时 `template_id` 有三种填法，**语义不同**，不能混：

| 传值 | 含义 | 库里落什么 |
|---|---|---|
| 不传 / `null` | 帮我挑 | `pick_template` 的结果 |
| `""` | 明确不套模板 | `NULL`（这一列是指向 templates 的外键，空串不是任何模板的 id） |
| 具体 id | 用户选的 | 原样 |

`pick_template(kind, subtype, channel)` 按链取第一个命中：

1. `kind + subtype + channel` 且 `is_default=1`
2. `kind + subtype` 且 `is_default=1`
3. `kind + channel` 且 `is_default=1`
4. YAML 里 `subtypes.<subtype>.template` 声明的出厂默认
5. 该 `kind` 下任意一个模板
6. 空——S0 不出内容，退化为无骨架写作

第 2 级排在第 3 级前面是有意的：**文种比渠道更接近内容本身**。给「技术 + 知乎」挑骨架时，一套专门为技术文写的通用骨架比一套只为主流平台写的通用骨架更贴题。

### 2.5 模板库：内置只读，复制才改

YAML 是内置模板的唯一事实来源，每次启动覆盖 `is_builtin=1` 的行。所以界面上对内置行的一切直接改动都被拒绝（PATCH / DELETE 返回 409，detail 指路「请先复制一份」）；改内置模板的唯一入口是 `POST /studio/templates/{id}/duplicate`。用户复制出的副本 `is_builtin=0`，升级不会被冲掉。

删模板前先解绑用到它的作品（`UPDATE works SET template_id=NULL`），返回解绑了几本。作品跟着消失是灾难，模板悄悄失效是骗人——两件都不能接受。

「从本篇沉淀模板」（`POST /studio/templates/from-work/{work_id}`）只用已经写出来的东西反推，不调模型：读 `ordinal IS NOT NULL` 的节点按序排，节数与源作品一致，最多 30 节（超出截断并在返回的 `truncated` 里说明）。`heading` 取节点标题，`prompt` 优先取节拍卡 `summary`（比正文前 120 字更说明「这节要写什么」），`target_words` 取该节实际字数（为 0 时兜底 800），`checks` 与 `style_prompt` 取自源作品自己的 `resolve` 与文风。

## 3. 通用生成流程

```
选题 + 素材
   ↓
article_outline   生成标题候选 3 个 + 按模板填充节骨架
   ↓  人工确认（可跳过）
section_draft     逐节生成，每节独立装配上下文（S0/S1/S2/S_src/S7/S8）
   ↓
assemble          拼接 + 补过渡句 + 统一称呼与格式
   ↓
fact_check        来源核对 + 时效核对 + 术语核对
   ↓
polish            可选的润色
```

**为什么逐节生成而不是一次生成全文**：
1. 网页端单次输出 5,000 字极不稳定，容易中途断流
2. 每节可以单独重生成，不用整篇重来
3. 每节只装配相关素材，比把全部素材塞进一次 prompt 更准

**代价**：节与节之间可能重复或断裂，所以 `assemble` 这一步不能省。它专门负责三件事：去重开头的承接句、补过渡句、统一称呼与格式。

## 4. 五种文种各自的骨架要点

### 4.1 历史

| 项 | 内容 |
|---|---|
| 骨架 | 背景 → 事件经过 → 影响 → 史料辨析 → 结语 |
| 语气 | 书面、克制、不用现代网络用语；对存疑处明确写「一说」「存疑」 |
| 素材要求 | **每条史实必须有来源**（书名/论文/档案），至少 3 条独立来源 |
| 检查 | `citation_missing`（年份/人名/事件无来源，硬）、`number_unsourced`（带单位的数字对不上已登记素材，软/info，已实现）；`claim_unverified`（陈述与事实矛盾）未实现——要语义对齐才能判，交给人 |

提示词要点：

```
只使用 <sources> 中提供的事实。凡涉及年份、人名、地名、数字，
必须能对应到某条 source；无法对应的内容改用「据…记载」并标注存疑。
不要补充你记忆中的人物生卒年、战役兵力等具体数字。
```

常见失败：模型凭训练记忆补「具体年份与兵力」，读起来很专业但全是错的。**这一类必须强制走素材模式，不能走纯 prompt 模式。**

### 4.2 时政

| 项 | 内容 |
|---|---|
| 骨架 | 事实陈述 → 多方立场 → 影响推演 → 结论 |
| 语气 | 中性、陈述式；区分「事实」与「观点」 |
| 素材要求 | 素材必须带 `published_at`；prompt 注入「资料截止日期」 |
| 检查 | `fact_stale`（引用过期事实，硬）、`citation_missing`（硬）、`number_unsourced`（软/info，已实现） |

提示词要点：

```
资料截止日期：{cutoff_date}。
只依据 <sources> 中的材料；材料未覆盖的事件一律不写。
涉及多方立场时，每种立场单独成段并标注来源，不做立场判断。
所有结论必须标注为「分析」或「推测」。
```

两个硬约束：
1. **时效**：`facts.valid_until` 过期即报 `fact_stale`。时政类事实的半衰期很短，方案里把它做成硬规则而不是提醒。
2. **联网**：可选用 DeepSeek 的搜索模式补充最新信息（`extra_body={"search": true}`），但搜索结果**必须先入 `sources` 并人工确认**，不能直接进正文。

### 4.3 技术

| 项 | 内容 |
|---|---|
| 骨架 | 背景 → 方案 → 步骤 → 坑 → 结论 |
| 语气 | 直接、不寒暄、不用「首先其次最后」；术语统一 |
| 素材要求 | 官方文档、版本号、命令输出；版本号必须写清 |
| 检查 | `term_inconsistent`、`structure_incomplete`、代码块完整性 |

提示词要点：

```
面向 {audience}。每节开头直接给结论，不写「随着…的发展」这类铺垫。
代码块必须带语言标注；命令与配置分开；不要省略「…」之外的内容。
涉及版本差异时写明版本号；不确定的 API 签名不要编，改写为「参考官方文档」。
```

**代码块截断是本类特有的坑**：上游流式输出被 `max_tokens` 软截断时，可能停在代码中间。方案里在 `section_draft` 结束后做一次校验：

```
扫描未闭合的 ``` 围栏 → 若存在，追加一次「继续输出未完成的代码」续写
```

这是少数必须做后处理的地方，因为半截代码对技术文档是致命的。

### 4.4 生活推荐

| 项 | 内容 |
|---|---|
| 骨架 | 场景 → 清单 → 对比 → 建议 |
| 语气 | 口语化、第二人称、短句；可用具体场景代替形容词 |
| 素材要求 | 可宽松，但价格/参数需标注来源与日期 |
| 检查 | `absolute_claim`（广告法风险词，软/info，已实现）、`fact_stale` |

`absolute_claim` 的实现只收「有领域的吹嘘」：最佳/性价比最高/销量第一/唯一值得买/100%/稳赚不赔。**裸「第一」与裸「唯一」不收**——「第一步」「第一类」「唯一凭据」是普通用法，真实语料里这条的误报全部来自裸词（参 `app/studio/soft_rules.py:ABSOLUTE_RE`）。

提示词要点：

```
用第二人称、口语化表达，像朋友推荐而不是广告文案。
禁止使用「最好」「第一」「唯一」「国家级」「100%」等绝对化表述。
每条推荐必须给出适用场景与不适用场景，不要只说优点。
涉及价格时标注「参考价，以实际为准」并写明查询日期。
```

常见失败：整篇都是「非常适合」「强烈推荐」，没有具体信息。解决办法是在模板里强制每节带一个「不适合谁」的小段。

### 4.5 通用单篇

兜底模板：引言 → 主体（2-4 节） → 结论。没有特殊检查，只有 `structure_incomplete` 与字数偏差。用于报告、总结、方案、随笔等未归类内容。

### 4.6 系列型非虚构（article.scale=series）

场景：20 讲课程、5 万字行业报告、非虚构书（人物传记/商业案例）、系列专栏。

与单篇的差别不是「更长」，而是多了三样东西：

1. **中间层摘要**：节 → 讲 → 全书。没有讲摘要，写到第 7 讲时上下文里找不到「第 3 讲讲的是什么」
2. **交叉引用**：「如前所述」「见第 3 讲」需要能自动校验目标是否存在
3. **术语一致性更严**：跨 20 讲，同一个概念不能有三种叫法

结构：

```
篇（可选）
 └ 讲/章（8-60 个，ordinal 全序）
     └ 节（每讲 2-5 个）
         └ 子节（可选）
```

流水线在单篇基础上多一步，且**目录必须人工确认**：

```
series_outline   生成讲目录（每讲一句话说明）
  → 人工确认目录    这一步必须人工，目录错了后面全废
  → lecture_beats 每讲的节骨架
  → section_draft 逐节
  → assemble
  → cross_ref_check  交叉引用与术语校验
  → fact_check
```

为什么目录必须人工确认：20 讲的目录如果 AI 把「进阶」排到「基础」前面，后面 20 万字全部作废。这是全流程唯一一个强烈建议不跳过的人工卡点。

引用检查规则（`cross_ref_check`）：

| 检查 | 处理 |
|---|---|
| 正文出现「第 N 讲」| 解析目标，校验该讲存在且序号对应 |
| 「如前所述」「见下文」| 向后/向前搜索是否存在对应内容，找不到告警 |
| 术语命中 forbidden | 硬告警 |
| 同一概念在术语表有多条 | 合并提示 |

系列型的装配差异：`S2` 桶装「全书概要 + 讲目录」，`S4` 装「相邻 2-3 讲的摘要」，不再装全部节摘要。

## 5. 素材库使用规范

素材是单篇质量的上限。用法上有四条硬规则：

1. **单条素材 ≤ 20,000 字**。超过先摘要或拆分，否则检索块会把预算吃光。
2. **入库必带日期**。`published_at` 空着的素材，在时政/历史类里降权 50%。
3. **引用必须可追溯**。正文里的每个数字、年份、结论，都要能对应到 `facts.source_id`。
4. **去重**：URL 相同直接拒收；正文相似度 > 0.95（SimHash 或前 200 字比对）合并。

素材分块与正文共用 `chunks` 表，`source_kind='source'`，块大小 500 字（比正文的 800 字更细，因为素材密度高、需要精确定位）。

## 6. 事实卡与时效

`facts` 表是素材与正文之间的中间层，作用是**把「一段素材」压成「一条可引用的事实」**：

| 字段 | 含义 | 例子 |
|---|---|---|
| statement | 事实陈述，一句话 | 某框架 2.0 于 2026 年 9 月发布 |
| source_id | 来源 | 官方 changelog |
| valid_until | 有效期 | 2027-01（下个版本发布前） |
| confidence | 置信度 | 0.9（官方来源）/ 0.6（二手转述） |

抽取时机：素材入库后异步抽取一次，人工可编辑。装配时按「相关度 × 新鲜度」排序取 Top 10 进 `S_src` 桶。

新鲜度算法：`exp(-(今天 - published_at) / 180天)`。半年衰减到 0.37，一年衰减到 0.13。时政类把半衰期设为 30 天。

## 7. 术语表

技术类文档的口径统一靠 `terms` 表，一条记录四段：

```
term: 云原生
definition: 以容器、微服务、声明式 API 为基础的应用构建方式
preferred: 云原生
forbidden: ["云原生技术", "云原生架构技术"]
```

装配时**不全量塞**，只带本节检索命中的 Top 20。全量塞 200 条术语会白白吃掉 2,000 字预算，还会让模型过度关注措辞而忽略内容。

检查时机：`section_draft` 完成后跑一次正则扫描，命中 `forbidden` 直接报 `term_inconsistent`，纯字符串匹配，零成本。

## 8. 验收清单

单篇写完，按这张表自查（前端可做成勾选项）：

| # | 检查项 | 适用 |
|---|---|---|
| 1 | 每节都有明确结论句，不是铺垫 | 全部 |
| 2 | 所有数字/年份/版本号有来源 | 历史/时政/技术 |
| 3 | 没有「首先/其次/最后」「随着…的发展」 | 技术/通用 |
| 4 | 每节字数在目标 ±40% 内 | 全部 |
| 5 | 代码块闭合、带语言标注 | 技术 |
| 6 | 无绝对化用语 | 生活推荐 |
| 7 | 术语写法与术语表一致 | 技术 |
| 8 | 时政类所有事实在有效期内 | 时政 |
| 9 | 节与节之间无重复开头 | 全部 |
| 10 | 结论给出适用边界，不只是总结 | 技术/通用 |
| 11 | 段落节奏符合所选渠道（公众号每段 ≤3 行、小红书开头三行给利益点） | 选了渠道时 |

## 9. 三种形态的切换

同一个工作台，`kind` 与 `scale` 决定右栏与流水线：

| 入口 | 小说 | 单篇 | 系列非虚构 |
|---|---|---|---|
| 新建 | 选题材 + 目标字数 | 选类型 + 渠道 + 模板 | 选类型 + 讲数 |
| 左栏 | 卷/章树 | 节大纲树 | 讲/节两级树 |
| 右栏 | 设定卡 / 人物状态 / 图谱 | 素材 / 事实卡 / 术语 / 模板 | 同单篇 + 讲摘要 |
| 主操作 | 章纲 → 草稿 → 续写 | 大纲 → 逐节 → 拼装 → 核查 | 目录（人工确认）→ 逐讲 → 拼装 → 引用校验 |
| 批量 | 20 章无人值守 | 一天 20-30 篇 | 一次 1 讲（约 30-60 分钟） |
| 人工卡点 | 每 10 章抽检 | 无 | 目录必确认 + 每 5 讲抽检 |

三种形态共用：编辑器、版本历史、上下文预览、任务队列、导出、LLM 网关、素材与术语。

## 10. 一个装配示例

技术类第 3 节「落地步骤」的 `context/preview` 输出（节选）：

```json
{
  "buckets": [
    {"id": "S0", "chars": 620, "budget": 1000},
    {"id": "S1", "chars": 480, "budget": 1500},
    {"id": "S2", "chars": 1240, "budget": 4000},
    {"id": "S_src", "chars": 5680, "budget": 6000},
    {"id": "S7", "chars": 3100, "budget": 8000},
    {"id": "S8", "chars": 180, "budget": 1000}
  ],
  "total_chars": 11300,
  "warnings": ["S_src 触发预算截断，丢弃 2 条低相关素材"]
}
```

对应的 user 消息骨架：

```xml
<template>技术方案：背景→方案→步骤→坑→结论（5 节，当前第 3 节）
渠道：知乎</template>
<style>面向有经验的后端工程师；直接、不寒暄；代码块带语言标注
平台要求（知乎）：先给结论再给论证，允许分点；每个判断后面跟一个具体例子</style>
<work_brief>给现有 Python 服务接入本地向量检索，替代 Chroma</work_brief>
<sources>
  <source title="某库官方文档 v2.1" date="2026-09" url="https://...">...</source>
  <fact valid_until="2027-01">该库 2.1 版本支持 SQLite 后端</fact>
</sources>
<terms>「向量检索」统一写法，禁用「向量搜索」</terms>
<current_draft>## 方案概述\n（已写 1,240 字…）</current_draft>
<instruction>写第 3 节「落地步骤」，分步骤说明安装、建索引、查询，每步给命令与预期输出</instruction>
```

这个示例体现了一个设计原则：**素材与事实进 `<sources>`，口径进 `<terms>`，当前进度进 `<current_draft>`，三者互不混用**。混在一起时模型会分不清「哪些是事实、哪些是要求」。同类地，S0 里的「渠道」一行与 S1 里的「平台要求」一段不能并进文体要求：前两者说「发到哪」，后者说「写什么领域」，混成一句时模型会拿其中一条把另一条顶掉。

## 11. 加工类任务

日常写作里，「从零写」可能只占一半，另一半是加工已有内容。这类任务不属于任何作品，硬塞进作品模型会很别扭。

| 操作 | 输入 | 输出 | 典型场景 |
|---|---|---|---|
| `rewrite` | 长文 + 目标风格 | 改写后全文 | 学术稿 → 公众号稿 |
| `condense` | 长文 + 目标字数 | 摘要 | 会议记录 → 300 字简报 |
| `expand` | 大纲/要点 | 成文 | 提纲 → 初稿 |
| `merge` | N 篇素材 | 综述 | 10 篇资料 → 1 篇行业综述 |
| `split` | 一篇长文 | N 条碎片 | 长文 → 10 条朋友圈 / 5 篇系列 |
| `translate` | 原文 + 目标语言 | 译文 | 英文文档 → 中文 |

与生成任务的差别：不需要作品树（输入即上下文），不写 `nodes` 表，结果直接返回；但可「另存为作品」作为后续加工的起点。

`POST /studio/transform {input, op, target, options}`

四个实现要点：

1. **长文改写要分块 + 拼接**：2 万字不能一次塞。按节切分逐块改写，最后统一过渡——这与单篇的 `assemble` 是同一套逻辑，直接复用。
2. **`condense` 要保留数字**：摘要最容易丢具体数字，而数字往往是最有价值的信息。提示词强制「保留所有数字与专有名词」。
3. **`split` 要先定切分维度**：按时间、按主题、按观点？不定维度切出来的碎片会互相重复。
4. **`translate` 不要逐句直译**：按段落重写保持语感，术语表在这里同样适用。

加工任务不需要图谱、不需要摘要、不需要任务队列（一次调用 1-2 分钟，直接等即可）。它是整个系统里最轻的一环，但使用频率可能最高。
